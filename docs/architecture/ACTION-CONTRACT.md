# Action Contract v0.1

ActionEnvelope is an internal Guard object. It includes the HTTP Idempotency-Key supplied by Runtime, a server-generated operation_id, authenticated subject/actor/workload/tenant context, resolved capability binding/version, target resource, normalized arguments, risk context and trace/correlation references. The ActionRequest body does not supply operation_id, tenant, subject, actor, tool-binding digest, policy version or executor audience. Identity fields asserted by a caller are checked against authenticated context.

CanonicalAction is schema-validated, default-expanded and normalized before hashing. ActionHash binds schema version, subject/delegation, capability id/version, target, canonical arguments, policy/binding digest and audience.

Decision: ALLOW | DENY | REQUIRE_APPROVAL. Approval never overrides DENY. Permit is one-time, short-lived, audience-bound and operation-bound. Executor verifies Permit, ActionHash, binding digest, expiry and claim before effect.

Authorization decision and Operation lifecycle are separate state axes. Decision: ALLOW | DENY | REQUIRE_APPROVAL; approval never overrides DENY. Operation: PENDING → CLAIMED → DISPATCHING → SUCCEEDED | FAILED_CONFIRMED | UNKNOWN; UNKNOWN → RECONCILING → SUCCEEDED | FAILED_CONFIRMED | MANUAL_REVIEW. CANCELLED_BEFORE_DISPATCH is allowed only while no external request could have been sent. FAILED_CONFIRMED requires authoritative evidence. Receipt includes server-generated operation_id, Guard-generated executor attempt_id (wire field attempt_id), action_hash, executor identity, target reference, result digest, timestamps and verification outcome.


## Submission identity and retries

- Runtime sends a stable Idempotency-Key header for one logical ActionRequest. It is created and persisted by Runtime before first submission.
- EngageGuard scopes the key by tenant and computes RequestHash over the normalized request plus authenticated identity context.
- Same tenant + Idempotency-Key + same RequestHash returns the same server-generated operation_id and current Operation status.
- Same tenant + Idempotency-Key + different RequestHash returns 409 IDEMPOTENCY_KEY_REUSED. It never creates a second Operation.
- operation_id is generated by EngageGuard on first accepted submission; it is not supplied in the ActionRequest body.
- attempt_id is Guard/Trusted Executor-owned and changes for each concrete execution attempt.

## Compute delegation boundary

For a protected compute capability, the Compute Control Plane is the trusted enforcement point for provider mutations. EngageGuard issues a one-time Permit bound to the exact CanonicalAction and Compute CP audience. Compute CP validates the delegated Permit/action binding before provider dispatch and creates its own compute_operation_id. EngageGuard owns the protected Action Operation and Receipt; Compute CP owns provider_request_digest, provider attempts and UNKNOWN reconciliation. The two journals are linked by references, not merged.

A Compute Workload acceptance response is not proof of a BOUND Allocation. A Guard Receipt must not claim compute readiness unless Compute CP has authoritatively reported the required Allocation state.
